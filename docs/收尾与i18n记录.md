# 收尾记录：中英双语、主题适配、以及 roadmap 的三项

日期 2026-09-25 · 版本 0.1.1 → 1.0.0

（0.2.0 曾短暂发布，系版本号写错所致；随后以 1.0.0 重发，代码内容相同。）

这一轮把 README「后续计划」里最后四项做完（自动命名 / 历史检索分页 / 推理可折叠 /
English README），并补上中英双语与主题适配。下面是**设计决定**、**自查出的问题**与
**验证边界** —— 下次改这三块之前先读这里。

## 一、界面语言（i18n）

- **两半端各有一份词表**：界面半端 `lib/client.js` 的 `MESSAGES`（101 键 × zh/en），
  宿主半端 `lib/index.js` 的 `PROMPTS`（系统提示词 + 分节标题 + 兜底问句 + pin 文案）。
  两边不共享模块：宿主是 Node 侧、界面是手写加载器模块，共享要引入构建步骤，不值。
- **语言从哪来**：设置项 `lang` 取 `auto | zh | en`（默认 `auto`）。
  `auto` 的顺序是 **`<html lang>` → `navigator.language` → zh**。
  诊断页把「最终选中了哪种语言 + 依据是什么」摊开显示（`langSource()`），
  所以 `auto` 不是一个黑盒猜测。
- **只翻译界面与提示词**：选中文字、所在消息、`context.md`、命令、路径、路由名、
  参数值一律原样传递。
- **界面语言随请求走**：`/explain` 与 `/pin` 的 body 带 `lang`，宿主据此选提示词模板。
- 语言在参数页切换后**立即重绘**（`reopenSettings('params')`），不必重开面板。

## 二、主题适配

- 所有表面改为经 `--loupe-*` 中转到宿主设计令牌，而不是每处直接写
  `var(--dsw-xxx, 兜底)`。兜底分**深浅两套**，由容器上的 `data-loupe-scheme` 选择。
- 深浅解析顺序：**宿主在根元素声明的 `color-scheme` → 系统偏好**（`themeScheme()`）。
  于是：浅色宿主 + 深色系统仍用宿主的浅色（令牌永远胜出）；宿主没给令牌时按系统兜底，
  不会出现白底黑字压在深色页面上。
- `color-scheme` 一并声明，原生控件（select / textarea / 滚动条）跟着变。
- 监听 `prefers-color-scheme` 变化，面板开着也能即时切换。
- 诊断页显示：当前深浅 + **宿主设计令牌是否可用**（`hostTokensAvailable()` 实测
  `--dsw-alias-bg-base` 是否解析出值），主题适配到底生效没有一看便知。

## 三、三项功能

- **历史搜索与分页**：`/history` 新增 `q`（划选内容 / 问题 / 答案，大小写不敏感）、
  `offset`，返回 `matched` 与 `hasMore`。界面端 250ms 防抖搜索 + 「加载更多」。
  实现上**只映射要返回的那一页** —— 先扫一遍数匹配数，命中第 offset..offset+limit 条
  才做投影，不为翻一页把上万条答案正文读进内存。
- **推理过程可折叠**：宿主不再丢弃推理分片（`createChunkReader` 现在同时返回
  `text` 与 `reasoning`），新增 SSE `reasoning` 事件；界面端建一个默认收起的
  `<details>`。历史留档上限 **4000 字**（`reasoningChars` 记录原始长度），从历史复原时
  折叠块里还有内容。
- **保存后的会话自动命名**：走宿主的 `sessionTitle` 服务
  （`ctx.get('sessionTitle').rename(bound.session, '划词 · <词>')`，与 better-sidebar
  的侧边线程同款调用）。**没有该服务就保留宿主自动标题**；命名抛错只吞掉，
  不让保存失败。

## 四、这一轮自查出来的问题（都不是新功能带来的，是被新工作照出来的）

1. **词表被脚本替换污染**：用「字符串替换」接线的第一遍把**词表自身**的值也改了，
   变成 `explain: t('explain')` —— 自调用，取一次文案就无限递归。
   根因是替换范围没有排除词表区域。修法：从 pristine 副本整段回灌 + 加两道校验
   （词表内不得出现 `t(`；键集两语言必须一致）。
   **教训：脚本化改写文本时，必须显式排除「这些字面量被定义的那一段」。**
2. **设置面板会叠出第二个**：`openSettings()` 只关了浮窗（`if (win) closeWindow()`），
   没有关掉已存在的设置面板 —— 重复点「设置」会出现两个面板、各带一份拖拽监听。
   已改为单实例（进入时先 `closeSettings()`），并让关闭按钮统一走 `closeSettings()`
   以便拆掉 window 监听。
3. **probe 的版本号写死**：发布 0.1.1 之后它仍报 `0.1.0`。改为从 `package.json` 读。

## 五、验证方式与边界

- `node --check` 两半端。
- 词表冒烟（本机临时脚本，不入库）：解析出词表对象，逐键求值 ——
  两语言各 101 键、键集完全相同、值都是非空字符串、**不含 `t(` 自引用**。
- **最小 DOM 桩端到端**（本机临时脚本，不入库，29 项全过）：
  真的加载模块 → `apply()` → 合成选区 → 浮标出现 → 点「解释」开出浮窗 →
  `/explain` 被调用 → 打开设置面板 → 四个页签逐页渲染 → 切英文后**文案与页签同时变** →
  历史页带 `offset`/`q` 请求 → 深色宿主下新面板带 `data-loupe-scheme="dark"`。
  它也照出过桩自身的缺陷（`textContent=''` 未清空子节点、`remove()` 未摘除节点），
  修桩后才算数。
- **边界**：这不是真机验证。宿主半端改了路由与提示词，必须**重启 profile** 才生效；
  界面半端刷新页面即可。真机复验之前不要宣布"已验证"。

## 六、已知限制

- 搜索与分页的范围是**可读窗口**：`history.jsonl` 超过 8MB 时只读尾部 2MB，
  所以 `total` 是窗口内的条数，不是文件全量。要全量得改成流式扫描。
- 推理留档截到 4000 字，更长的推理在历史里会缺尾部（当次界面显示是完整的）。
- 英文版 README 沿用中文界面截图（本机既有取舍，不为它切应用语言重拍）。

## 七、真机第一反馈：插件显示成英文（2026-09-25，重启后立刻发现）

**现象**：重启 profile 后插件界面全英文。用户问「为什么现在我的语言是英文」。

**根因（取证，不是猜）**：我把 `document.documentElement.lang` 当成了「宿主界面语言」，
而宿主前端的模板 `@deepseek-ai/dsh-web-frontend/dist/index.html` 第 2 行**写死**
`<html lang="en">`，与用户实际语言无关。用户的 `settings.yaml` 里**没有** `locale:` 段
（只有 `ui-theme:`），按宿主 `dsh-client-locale` 的设计「没有偏好时委托给浏览器」，
GUI 语言 = 浏览器语言 = 中文 —— 只有本插件被那个固定值带偏。

**改后的判断链**：显式设置 → 宿主 `settings.yaml` 的 `locale.preference`
（新增 `GET /plugins/dsh-loupe/locale`，宿主半端读文件）→ `navigator.language` → zh。
`<html lang>` 降级为诊断页的一行说明，明确写着「模板固定值，不参与判断」。

**主题那半边本来就取对了**：宿主 `dsh-client-ui-theme` 的启动脚本会把
`ui-theme.preference`（light / dark / system）解析后写进
`document.documentElement.style.colorScheme`（同一份实现里也写 `body[data-ds-dark-theme]`），
本插件读的正是它 —— 所以深浅判断不需要改。

**测试为什么会漏掉它**：DOM 桩里写了 `documentElement.setAttribute('lang','zh-CN')`，
等于把我自己的错误假设当成了前提，「通过」是假的。桩已改为 `lang="en"`（与真实宿主一致），
并新增两条用例：① `html lang=en` + 浏览器中文 → 必须显示中文；
② 宿主 `locale.preference=zh` + 浏览器 `en-US` → 必须显示中文（宿主优先）。

**教训**：桩里的每一个「宿主事实」都必须来自取证 —— 目录里读到的、宿主源码里核过的，
不能来自我的假设。假设进桩，测试就变成自我确认。
## 八、issue #1：模型解析两档同时失效，/explain 一律 503（2026-09-25）

**报告**：`twinkle-yj0` 在 GitHub 上提了 issue #1，附完整 `model.tried` trail 与源码级根因。
**本机复现**：同一份 trail（`service agentDefaultModel: present but no {provider,model}
shape (keys: ctx,name,ownerContext,config)` + `settings.yaml: ENOENT`），所以这不是
「只有他遇到」的环境问题。

**根因**：`resolveModel()` 第 2 档的候选方法名里**漏了 `currentSelection`**。
宿主 `@deepseek-ai/dsh-agent-default-model` 的 `AgentDefaultModelConfig` 只暴露
`currentSelection()`（宿主自己也是这么用的：`dsh-headless/lib/index.js`、
`dsh-webhook/lib/index.js`）与 `saveSelection()`；`self` 兜底拿到的是 cordis
`Service` 实例，键恒为 `{ ctx, name, ownerContext, config }`，必然无 `{provider,model}` 形状。
**第 3 档同时失效**：新版 DSH 已把 `settings.yaml` 迁移走（本机只剩
`settings.yaml.imported`），而默认模型本来就在 profile 的 patch 里、由上面那个服务
读出来 —— 所以读文件这条历史路径在这台机器上本来就该 ENOENT。两档同断 → 503。

**修复（1.0.1）**：
1. 候选表补 `currentSelection` 并放第一位；
2. 失败 trail 改成如实列出「有哪些可读方法 + 服务自身键」，不再只报形状不符；
3. 第 3 档注明它是旧版位置、迁移后预期就是 ENOENT；
4. 语言偏好同样改为优先读宿主 `settings` 服务（同一个存储迁移病因），文件解析降为兜底；
5. **新增宿主半端集成测试**（假 ctx 驱动真实路由）：解析链、SSE 推理分片透传、
   历史检索分页、未知路由 404，共 18 项。这个 bug 能进 npm，正是因为宿主半端此前
   **零自动化覆盖** —— 补测试比补注释更值。

**没有采纳的两条建议**（issue 里提到、我判断不该做）：① 不把 profile 的 patch 文本
纳入第 3 档 —— 服务本身持有那两份 Config 引用，修好第 2 档即覆盖，再解析一份 patch
只是多一个会过期的真相来源；② 不让 `self` 兜底直接读 `svc.config` 的形状 ——
实测 `config` 是 Config 引用，`provider` / `model` 各自是一个 `.get()`，直接取形状不可靠。
