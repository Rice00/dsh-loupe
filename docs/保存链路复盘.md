# 保存链路复盘：一次「保存」踩穿的七个坑

> 2026-09-22。从"点保存没反应"到真正跑通，花了六轮真机往返。
> 本文按**因果链**而不是发现顺序记录 —— 因为这条链里每一环都伪装成上一环的结论。

## 最终正确的链路

```js
const sessionId = await sessions.create({ workspaceId })   // 建档 + 入账（host 自动 attach）
const bound = sessions.binding(sessionId)
await bound.session.prompt([{ type: 'text', text: transcript }], 'queue')
```

就这两步。中间任何"自己再补一步"的尝试都是错的（见坑 5、6）。

---

## 七个坑

### 1. host 的 seed 事件：data 层级按类型不同

- **现象**：`seed user/message at index 0 lacks an identified message`
- **根因**：`user/message` 的 data **就是 message 本身**（扁平：`content` / `source` / `role` / `id`）；只有 `assistant/message` 才包一层 `{ message }`。校验按类型分支取值：

  ```js
  const message = type === 'user/message' ? record : record?.['message']
  ```

- **修法**：message 直接放进 `data`，并补上真实事件带的 `surfaceOp: 'append'`

### 2. session/prompt：content 必须是 ContentBlock[]

- **现象**：`client api: session/prompt rejected "request"`
- **根因**：prompt 实现里有 `content.some(part => part.type === 'file')` —— content 被当数组使用，传字符串被参数校验拒绝
- **顺带澄清**：`requestId` **不是**必需的（实现里是 `requestId ?? randomUUID()`），我一开始怀疑错了对象
- **修法**：`prompt([{ type: 'text', text }], 'queue')`

### 3. 工作目录：不要猜

试过并全部失败的路线：

| 尝试 | 结果 |
| --- | --- |
| DOM 选择器（`button[aria-label*="工作目录"]`、`[data-path]` …） | 猜不到 |
| `sessions.list.getSnapshot().current → byId[current].cwd` | 拿到的 cwd 仍落错地方 |
| **最终** | **不猜**：把工作区列出来让用户选 |

### 4. 工作区列表：快照读取面在 `service.list` 上

- **现象**：选择器显示「宿主没有报告任何工作区」
- **根因**：服务对象 `WorkspaceController` 的构造是 `super(ctx, 'workspaces'); this.list = model` —— **快照读取面在 `service.list`**，service 本身只有命令方法（create / rename / insertSessionBefore …）
- **修法**：两个位置都试，谁有 `getSnapshot` 用谁

### 5. 入账：`cwd` 与 `workspaceId` 语义完全不同（最终根因）

- **现象**：选了 dsh 工作区，会话仍进「未分组」
- **根因**（读 host 的 `session.create` 实现）：

  ```js
  cwd          → 只把会话建在那个目录，**不入工作区的账** → 落进「未分组」
  workspaceId  → 用 workspace.path 当 cwd，并自动 workspace.attachSession() → 进左侧列表
  ```

  两者**禁止同时传**（`gateway/bad-request`）。客户端那边甚至有个函数叫 `workspaceAttachSessionId`，注释写着 *"expose it immediately as Ungrouped"* —— 这正是「未分组」的确切来源。

- **修法**：`create({ workspaceId })`，其余交给 host

### 6. `insertSessionBefore` 是「重排」不是「入账」

它的校验原文：

```
cannot move session '…' in workspace '…': the session is not accounted
```

即它要求会话**已经入账**。我用它做首次登记，注定失败 —— 而那次的错误被 `.catch(() => null)` 吞掉了，于是"失败"和"没执行"在界面上长得一模一样。

### 7. `transcript` 未定义（纯粹自伤）

- **现象**：点「确定」后毫无反应；文件系统里近 15 分钟没有任何新会话
- **根因**：上一次整段替换 `saveCurrent` 尾部时，`const transcript = lines.join('\n')` 落在替换区间里被一并删掉。`commitSave(parts, transcript, …)` 抛 `ReferenceError`，在 click 回调里静默失败
- **修法**：恢复定义，并在 `commitSave` 入口加 `typeof transcript !== 'string'` 守卫（`typeof` 对未声明标识符不抛错，所以这道检查能在同类事故里给出可读提示）

---

## 两条更值钱的工程教训

### 教训 A：静默失败是最贵的失误（出现了三次）

1. `ctx.config` 在 cordis 里直接抛错，`?.` 挡不住（第一次真机就撞上）；
2. `.catch(() => null)` 吞掉 `insertSessionBefore` 的 "not accounted"；
3. 三条 `return null` 静默路径 + 一个 catch，让"没登记成功"和"根本没走到登记"完全无法区分。

**规矩**：任何"为了不阻断主流程"的 catch，都必须把原因**显示给用户**，而不是丢掉。

### 教训 B：整段替换函数尾部，两次吃掉闭合大括号

`saveCurrent` 一次、`commitSave` 一次。原因完全相同：替换区间的终点取 `"\n\n    // ── …"`，而边界上的 `}` 落在区间内。

**规矩**：替换前先读实际内容；写入前跑括号平衡自检（深度必须回到 0、最小深度不得为负）。

## 时间成本

六轮真机往返。其中**四轮本可避免**：坑 3（猜目录）、坑 6（用错 API）、坑 7（自伤）都属于"先查清楚再动手"能省下来的。

真正需要真机试错的只有坑 1、2、5 —— 它们依赖宿主的运行时约定，静态文档里查不到，只能靠实测报错倒推。

**一句话**：这一路上最有效的动作不是写代码，而是**去读宿主的实现**（`session.create` 的 30 行、`entity.js` 的 `attachSession`、`service.list` 的构造）—— 每一次读源码都直接终结了一轮猜测。
