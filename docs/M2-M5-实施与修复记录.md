# dsh-loupe · M2–M5 实施与修复记录

> 2026-09-22 深夜。M1 之后又经历了 4 次重启，本文记录 M2–M5 的落地、真机暴露的每个问题与修法、以及实测数据。
> 每条都写清「现象 → 根因 → 证据 → 修法」，便于复发时快速定位。

## M2 插件上下文（已完成并强验证）

- **接口**：`GET /plugins/dsh-loupe/context` 读、`POST` 写（上限 64 KB，超出截断并明确回报，不静默丢）
- **落盘**：`~/.dsh/loupe/context.md`
- **验证方式（端到端效果证据）**：写入一条术语约定后提问——
  ```
  context.md:  术语约定：在本项目里「loupe」专指 dsh-loupe 这个划词解释浮窗插件
  提问:        在本项目里这个词指什么？
  回答:        在本项目里，「loupe」专指 dsh-loupe —— 即这个划词解释浮窗插件本身
  ```
  回答**采纳了写入的约定**，不是"字段非零"这种弱证据。
- **设计**：这段文字放在 prompt 的**稳定前缀**里（system 段），吃宿主的前缀缓存；变化的部分（选区/所在消息）放后面。

## M3 历史（已完成，用户确认可用）

- **接口**：`GET /history?limit=N`，返回最新在前
- **读文件的保护**：history.jsonl 是无限追加的，超过 8 MB 时只读尾部 2 MB（列表页不需要全文，全读会卡住请求），并丢掉可能被截断的首行
- **UI**：设置面板「历史」页，点任意一条**复原回浮窗**继续聊
- **返回键**：从历史恢复的浮窗头部出现「←」，点它回到设置面板；正常划词进来的浮窗不显示（没有"来处"）

## M4 保存（已完成并全链路验证）

- **接口**：`POST /pin { text, title, cwd }` → `ctx.agents.create({ sessionId, meta, seed, signal })`
- **原理**：`seed` 是**预置的会话事件**而非 prompt——历史写得进去，但**不唤醒模型**，所以保存不会额外换来一次回答。刻意不设 `meta.origin`（better-sidebar 设 `'subagent'` 是为了把子会话藏起来），它就是左侧列表里的普通会话。

### 坑 1：seed 的 data 层级（`lacks an identified message`）

DSH 的两种 message 事件 **data 层级不同**：

```
user/message      → data 就是 message 本身（扁平：content / source / role / id）
assistant/message → data 包一层（{ message: … }）
```

校验源码（`dsh-session/lib/types/index.js`）按类型分支取值：

```js
const message = type === 'user/message' ? record : record?.['message'];
if (typeof message['id'] !== 'string' || message['id'] === '') throw new Error(`${subject} lacks an identified message`);
```

按 assistant 的习惯包了一层，`record['id']` 即为 undefined → 报错。改为扁平并补上真实事件带的 `surfaceOp: 'append'`。

### 坑 2：`_no-cwd`

不传 `meta.cwd` 时，会话落进 `~/.dsh/sessions/_no-cwd/` —— 一个伪工作区，在左侧列表里很突兀。better-sidebar 的做法是 `meta: { cwd: parentSession.header.cwd }`，它手里有父会话句柄，我们没有。

修法：client 从 DOM 多候选探测当前工作目录（会话头的「打开工作目录」按钮 title/data-path、侧栏当前会话项 data-path），随请求上报；**探测不到就不传**（退回 _no-cwd，功能照常，只是分组不好看）。

### 验证链（全链路证据）

```
POST /pin { cwd: "C:\\Users\\<user>\\Documents\\dsh" }
  → 200 { ok: true, sessionId: "session-174a47c5-…", hasAgent: true }
  → 会话落在 --C-Users-<user>-Documents-dsh-- （cwd 生效 ✓）
  → 日志 6 个事件：session / user-message(id,source,正文全部正确) / session-end-seed
                  / permission-preset / sandbox-mode / approval-policy（后三个宿主自动补）
```

## 自动累积（已完成，PLAN 中用户已同意）

每次解释成功后，把「选区 → 结论摘要」沉淀进 `context.md` 的**受控区块**（`<!-- dsh-loupe:auto:start/end -->` 之间）。

三个刻意设计：

1. **条目最新在前**——host 截断预算时从字符串尾部砍，倒序才能保住最近的条目；
2. **注释标记隔开**——用户手写的内容永远不会被累积逻辑碰到；
3. **失败静默**——累积是锦上添花，任何一步出错都不影响解释本身。

走已有的 `/context` 接口，因此**纯客户端改动、无需重启**。设置页可关。

## 本轮修复清单（真机暴露）

| # | 现象 | 根因 | 修法 |
| --- | --- | --- | --- |
| 1 | probe 报 `cannot get property "config" without inject` | cordis 对未 inject 的属性访问直接抛错，且 `?.` 挡不住 | 配置走 `apply(ctx, config)` 第二参数 |
| 2 | （重启前自查发现）Message 缺字段 | `Message` 要求 id/role/content/source | 读官方工厂源码后手写等价对象（`brandString` 是恒等函数） |
| 3 | 浮窗里出现一大段辅助上下文 | 推理分片与回答分片**都带 `text`** | 按 index 追踪 `blockType`，只渲染 text 块；未知类型保守当回答 |
| 4 | markdown 不生效 | M1 刻意用纯文本 | 用宿主共享的 `MarkdownText`（含流式模式），取不到时回退 |
| 5 | 浮窗拖不动 | **三个不同层次的原因**（见下） | 见下 |
| 6 | 偶发空回答留下空白 | provider 返回 0 字 | done 时 chars=0 → 明确提示"可重试" |
| 7 | 保存落到 _no-cwd | 未传 meta.cwd | client 探测 + host 转发 |
| 8 | seed 被拒 | data 层级包错 | 扁平结构 |

### 拖拽：同一个"拖不动"背后是三个层次

1. **事件阶段**——`mousemove` 挂在 document 上、走冒泡阶段，宿主在 capture 阶段拦截就永远收不到 → 改用 **Pointer Events + `setPointerCapture`**，监听提到 **window 的 capture 阶段**；
2. **CSS 兜底**——头部加 `user-select:none`，即便事件链路再出意外，拖动最多"不动"，不会退化成选择文本（回答区不加，那里要能复制）；
3. **结构缺失**——设置面板是 `openSettings()` 里自建的另一套 DOM，**从来没调用过 `makeDraggable`**。事件层修得再好也与它无关。

第三点最值得记：前两版修的都不是它。**排查"功能不生效"时，先确认那个元素到底有没有接上功能，再怀疑功能本身。**

## 已知边界（未验证 / 不确定）

- **client 的 cwd 探测**依赖若干 DOM 选择器（我无法使用浏览器验证，选择器是推断的）。探测失败会静默退回 `_no-cwd`。若长期不准，退路是在设置页手填工作目录。
- **`agentDefaultModel` 服务形状未知**：probe 显示 `present keys: ctx,name,source`，试探不到 `{provider, model}`。模型解析实际走 `settings.yaml` 兜底（该分支保留）。
- **`ctx.agents.create` 的参数形状**来自 better-sidebar 的实际调用（同版本 DSH），未见于官方文档；`meta.origin` 的取值空间未探明。
- **空回答偶发**：撞到过一次（10.5s、0 字、无任何 delta），复现两次均正常。已加提示，未定位到 provider 侧原因。
- **块类型判定**基于 `blockType` 实际取值（已见 `text` / `reasoning`）；宿主未来若新增块类型，未知类型会被当作回答显示——刻意选择的保守方向。
